# 存量全量迁 S3（下载链路 + HLS）设计

- 日期：2026-07-28
- 状态：设计完成，待实施
- 前置：`2026-07-27-storage-rust-io-consolidation-design.md`（PR1/PR2 已合入，PR3 前提被证伪未合并）

## 目标

把仍在文件系统上的媒体全部迁到对象存储，并让**新产生**的下载也直接落 S3，消除"两套存储并存"这一持续出错源。

HLS 部分已于 PR #1596 完成开关切换（`HLS_OBJECT_STORE: true`），新转码已落 S3 并实测可播；本 spec 处理**存量**与**下载链路接线**。

## 为什么值得做（实测，非推断）

三个尺寸段各测一次，方法学见 `scripts/bench-storage.py`（字节路径无 Python、清 page cache、扫并发）：

| 尺寸 | CIFS | S3 | 谁快 |
|------|------|-----|------|
| KB 级缩略图（串行 / 6 并发） | 8.8 / 0.6 ms | 13.8 / 1.4 ms | CIFS 2.3× |
| **~2MB HLS 分片**（串行 / 6 并发） | 68.4 / 37.6 ms | 8.1 / **1.5 ms** | **S3 25×** |
| 899MB 大文件（单流 / 8 并发） | 123 / 136 MB/s | 469 / **634 MB/s** | S3 4.7× |

CIFS 在中大文件上的瓶颈是 **SMB 单连接**：1→8 并发只涨 11%（`vers=3.0`，未启用 multichannel）。S3 侧随并发线性扩展。

**CDN 不是前提。** 大厂把 HLS 分片放对象存储的经济性靠 CDN（分片不可变、`max-age` 一年，一个视频看 1000 次源站只取 1 次），但本项目即使没有 CDN，S3 也已快 25×。

781 个文件系统行细分：

| 类别 | 数量 | 大小 | 说明 |
|------|------|------|------|
| 普通文件 | 612 | 19.8 GB | 可直接迁 |
| **图集目录** | 74 | — | `file_path` 指向**目录**而非文件 |

## 三个必须处理的既有问题

### 1. 图集是目录，不是文件

`file_path` 形如 `global/resources/web/douyin/281582206557042`，目录内容：

```
7613235931633607110_0.jpg   （slide）
cover.jpg                   （封面）
```

对象存储没有"目录"这一概念。2026-07-12 的首次生产 dry-run 正是因此失败 —— **70/880 行 `IsADirectoryError`**，导致当时决定"下载先不动"。

结构本身很简单（几个 jpg），难点不在展开，而在**展开后 `file_path` 存什么**：单行记录无法指向多个对象。

### 2. 95 行的文件已不存在

样例横跨新旧两种布局：

```
2026-02/7604567653499959450_.mp4                          （旧日期桶）
global/resources/web/douyin/7606134661488521073/video.mp4  （新布局）
```

**这是既有的数据完整性问题，不是迁移引入的** —— 这些资源在库里正常显示，点开才失败。迁移只会把它暴露出来。

### 3. 下载链路写入了错误的 `file_type`

```
S3 行(157)       file_type = image / audio / document / video    ✅
文件系统行(781)  file_type = 0 / 4 / 68 / 2 / 51（94 行为 video）  ❌
                 mime_type = video/mp4                            ✅ 正确
```

数字值是下载链路的遗留 bug。**不阻碍迁移** —— `MediaKeyBuilder.content_key_from_sha` 只需要 `mime`，而 `mime_type` 是对的。但应顺带修正。

## 设计决策

### 决策 1：图集展开为「目录前缀 + 清单」

单行 `file_path` 无法指向多个对象，三个方案：

| 方案 | 做法 | 取舍 |
|------|------|------|
| A. 打包成 zip/tar | 一个对象 | 读取需解包，播放器/前端全部要改 |
| **B. 前缀 + 清单**（选） | 各文件独立上传到 `sb://library/{scope}/album/{rid}/`，`file_path` 存**前缀**，清单存 `metadata` | 读取端需按前缀列举，但已有 `ObjectStore.list_prefix` |
| C. 拆成多行 | 每个 slide 一行 | 破坏"一个资源一行"的模型，影响标签/收藏等一切关联 |

选 B。理由：`list_prefix` 已存在且在 `HlsPublisher` 里验证过；HLS 本身就是"前缀 + master 清单"的同构形态，读取端已有处理多对象资源的先例。

**兼容性要求**：`resolve_media_source` 需能区分「单对象」与「前缀」。建议以尾部 `/` 标记前缀形态（`sb://library/.../album/{rid}/`），并在 `MediaLocation` 上加 `is_prefix` 属性，读取端据此分发。

### 决策 2：95 个失效行标记而非删除

新增 `resource_versions.storage_status` 列，取值 `ok` / `source_missing`。迁移时探测不到文件即标记，**不删除任何行**。

理由：删除不可逆；标记让当前静默的失败变可见（前端可据此显示"文件已丢失"而非加载转圈）；用户可在拿到完整清单后再决定。

### 决策 3：迁移用「复制 + 校验 + 后置删除」，不用移动

`storage_migration.py` 已有的三段式（PUT → UPDATE → 条件 unlink）保持不变：

1. `dry_run` 模式先跑全量，产出可迁 / 跳过 / 失败的完整清单
2. 正式迁移 `delete_source=False` —— 只复制，本地保留
3. 抽样校验 sha256 一致后，再单独跑一轮 `delete_source=True` 回收空间

**不允许一步到位的 move。** 19.8 GB 的不可逆操作必须有回退窗口。

### 决策 4：下载链路接线与存量迁移分开做

`downloader.py` 当前直接 `aiofiles.open()` 写盘，未接 `ObjectStore`。接线后新下载落 S3，但这与存量迁移是两件事：

- 先接线 → 停止累积新债务
- 再迁存量 → 一次性清理

顺序不能反：若先迁存量、后接线，迁移期间新产生的下载会继续落文件系统。

## 范围

### 做

| # | 内容 | 依赖 |
|---|------|------|
| 1 | `downloader.py` 接 `ObjectStore`，新下载落 S3 | — |
| 2 | `storage_status` 列 + migration | — |
| 3 | `MediaLocation.is_prefix` + 读取端分发 | — |
| 4 | `storage_migration` 新增 `downloads` 模块（含图集展开） | 1、2、3 |
| 5 | `storage_migration` 新增 `hls` 模块 | 3 |
| 6 | 存量迁移执行（dry-run → 复制 → 校验 → 回收） | 4、5 |
| 7 | 修正下载链路的 `file_type` 写入 | — |

### 不做

| 不做 | 原因 |
|------|------|
| 派生产物（缩略图 / sprite）迁 S3 | 实测 KB 级小文件 CIFS 快 2.3×；且它们可随时重新生成，无持久化需求。**上 CDN 时再迁**（届时 CDN 只能从对象存储回源） |
| 删除 95 个失效行 | 见决策 2 |
| 收编 `resources_crud_router.py` 的派生落位拷贝 | 上一个 spec 已记录三处兄弟位点，属独立重构 |
| 启用 Rust 流式 IO | 前提已被证伪，见上一个 spec 的事后结论 |

## 风险

| 风险 | 缓解 |
|------|------|
| 19.8 GB 迁移中断 | 三段式 + `dry_run`；`ObjectStore.exists` 做 skip-PUT，重跑幂等 |
| 图集读取端未覆盖 | 决策 1 的 `is_prefix` 分发必须先落地并测试，再迁数据 |
| 迁移期间新下载继续落文件系统 | 决策 4 的顺序：先接线后迁移 |
| 迁完发现读取变慢 | 已实测三个尺寸段；派生产物明确不迁（那是唯一 CIFS 占优的尺寸） |
| CIFS 上的源文件被提前删除 | `delete_source=True` 单独一轮，且在 sha256 抽样校验之后 |

## 验收

沿用 CLAUDE.md 的验收纪律 —— **读正常 ≠ 服务正常，必须写入冒烟**：

1. 每个迁移模块跑 `dry_run` 全量，清单与本 spec 的数字对得上（612 / 74 / 95 / 97）
2. 迁移后抽样 sha256 比对（本地 vs 对象存储）
3. 端到端：上传 → 下载 → 转码 → HLS 播放，全链路走一遍真实 API
4. 图集：前端能正常展示 slides（不只是 API 返回 200）
5. 95 个失效行：前端显示明确的"文件已丢失"，而非无限加载
