# 工作流下沉到剧集层 — 设计

日期:2026-08-04 ｜ 状态:待用户确认 ｜ 上游:M1-M4 工作流(项目级)已上线,#1677 打通个人项目入口后首次真实使用即暴露层级错误
配套:[`2026-08-04-screenwriting-agent-layer-design.md`](2026-08-04-screenwriting-agent-layer-design.md)(agent 工具/权限/隔离,可独立实施)

## 0. 问题

用户给「个人项目测试 1」挂上工作流后,当场提出三点,均成立:

1. **层级错了**。工作流是**项目级**、只有一个游标;而项目里有多个剧集,各自处在不同阶段。原话:"我这个 project 中有好几个剧本,那你 script 从哪里开始?"——项目级单游标无法表达这件事。
2. **左侧塞了配置**。侧栏出现 11 个阶段的列表,与顶部流程条重复,把创作导航(剧集/剧本/节拍/分镜/场景/成片)挤走。阶段与模板属于配置,应在设置里。
3. **阶段卡全是项目管理字段**(负责人/成员/排期/交付物/背景说明),单人创作场景下几乎全空。

同时存在**两套互不相识的进度**:剧集推导状态(自动数产物,`episode_repository.py:108-130`:无剧本→planned,有剧本→drafting,镜头未完→boarding,镜头完成→boarded,有成片→rendered)与工作流节点(人工点「完成阶段」)。

## 1. 目标架构

```
项目(一部剧)
├── 总览        = 多集汇总进度
├── 剧集(流水线的实际单位)
│   └── 每集一条节点链,每个节点二选一:
│         (a) surface 节点 → 就是剧集里那块创作面,点节点即进入
│         (b) 交付物节点 → 无 app 内内容,靠上传+版本+审阅完成
└── 设置        = 模板/阶段配置
左侧栏           = 只留创作导航,不放配置
```

**UI 沿用现有排布**:内容区顶部的分段控件位置不变(现为 `剧本 | 大纲 | 封面`),进入某节点时切换为该节点的视图集。

## 2. 关键决策一:分镜是**一个**节点、三种表现

用户指正(2026-08-04):`Storyboard / Canvas / Shot List` 是**同一个「分镜」节点的三种视图**,不是三个节点。

- **分镜**(默认视图):按场次分列,每列 = 场景元数据 + 该场镜头卡 + 「打开」「自动分镜」
- **画布**:底层仍是总画布;每个镜头是节点,含 `Storyboard`(画面/描述)与 `Lens`(景别/角度/运动/焦段)两页签
- **分镜列表**:同一批镜头的表格形态,按场次分组,便于通读与导出

因此模板中的 `Canvas (AI Generation)` 节点**并入 Storyboard**,不再作为独立阶段(见 §6 迁移)。

## 3. 关键决策二:推导状态 = surface 节点的自动完成信号

不设两套并行进度,否则必然出现"剧集说分镜中、工作流说还停在 Script"。统一为一套:

- **surface 节点**完成信号**来自产物**,复用现有推导阶梯。写了剧本 → Script 自动完成;镜头全出卡 → Storyboard 自动完成。用户不必点「完成阶段」。
- **交付物节点**没有 app 内创作面,完成靠**交付物 + 审阅**(现有上传/版本/审阅链路)。这里才需要人或 agent 推进。

剧集推导状态因此不再是独立系统,而是 surface 节点的完成判据;剧集列表上的标签与工作流游标同源,不可能打架。

## 4. 数据模型

| 改动 | 说明 |
|---|---|
| `project_stage_nodes.episode_id` | 新列(nullable)。节点归属剧集;NULL = 遗留项目级节点(§6) |
| 节点 `surface` 字段 | 模板节点声明它对应哪块创作面:`script` / `storyboard` / `renders` / `null`(=交付物节点)。取值集合随创作面增加而扩展,不在本设计里穷举 |
| 游标 | 从 `projects.current_node_id` 下沉为**每集一个游标** |

⚠️ **游标下沉是本设计最大的改动面,不是加一列那么简单**。`projects.current_node_id` 是 M1 的**活游标**(不是遗留列——遗留的是 `workflow_id`),而 `advance_service.py:357` 直接从**项目行**读它:`current_node_id = (project or {}).get("current_node_id")` → `_active_index(groups, current_node_id)`。整套推进/闸门机器(六道闸门、级联、autopilot tick、start-early)都假定"一个项目一个游标"。

因此下沉必须一并回答:每集游标存哪(建议 `episodes.current_node_id`)、`execute_advance` 的入参从 project 改为 (project, episode)、autopilot 的 tick 与配额是按项目还是按集计。**实施计划必须先做一次 `current_node_id` 的读写点全量盘点**,再动数据模型。

`canvases` **不加** `episode_id` —— 画布是分镜节点的一个视图,归属由分镜节点(进而由剧集)决定,不需要画布自己再挂一层剧集外键。(此条推翻本设计 2026-08-04 上午稿的「画布下沉」条目。)

## 5. 完成判据(surface 节点)

口径**部分**复用 `episode_repository._derive_episode_status`(`episode_repository.py:105-127`):

| surface | 完成判据 | 能否复用现有阶梯 |
|---|---|---|
| `script` | 该集有剧本**且有场次内容** | ❌ **不能**。现有阶梯只判 `script_count == 0`,同一条 SQL 虽算出 `scene_count` 却从未使用。需新写判据 |
| `storyboard` | `shots_total > 0 且 shots_done == shots_total` | ✅ 可复用(boarded 档) |
| `renders` | `renders_count > 0` | ✅ 可复用(rendered 档) |
| `null`(交付物型) | 交付物已上传且审阅通过 | 与推导无关,走审阅链路 |

判据变化时更新节点状态,挂在产物写入的既有回流点,**不新增轮询**。

**评审指出的三处缺口,已定案(2026-08-04):**

**① 产物删除 → 完成态回退,但游标不后退。**
两者是不同性质的东西:**派生完成态是关于产物的事实**(产物没了,事实就变了,必须回退);**游标是关于"活干到哪"的决定**(删一个剧本不代表整条流水线倒退)。所以:

- 删掉唯一剧本 → Script 节点显示未完成(派生值重算,自然为假)
- **游标原地不动**,不触发 `advance_service` 的 retreat,不重开已关闭的 mirror issue
- 想真的退回上一步,走**显式 retreat**(既有能力)

理由:自动回退会产生"删一个文件引发连锁倒退"的惊吓,而这条链上还挂着 mirror issue 与 agent 派发。派生值回退是诚实,级联倒退是危险。

**② 场景删除对镜头卡 — 现有行为已正确,无需改动。**
实测:`script_shots_scene_id_fkey` 已是 `ON DELETE CASCADE`。镜头卡脱离场景没有意义,级联删除是对的。`shots_total`/`shots_done` 是实时计数,级联后自然重算,不存在静默漂移。**本条从"待设计"降为"实施期加一条回归测试即可"**(断言删场后该集分镜判据正确重算)。

**③ `surface` 字段:模板与实例**各存一份**,实例在实例化时拷贝并冻结。**
沿用仓库已有的 `events` JSONB 惯例(模板层定义、实例化拷贝、实例冻结)。这样:

- 实例节点**自带 surface 值,不需要 join 回模板** → 评审担心的"遗留节点/手加自定义节点让 join 断裂"从根上不存在
- 模板改了不影响已跑起来的项目(与 `events` 的冻结语义一致)
- 遗留实例节点(`surface` 为空)按交付物型处理——最保守的降级

## 6. UI 改动

- **左侧栏**:删掉「阶段」列表。只留创作导航:剧集列表 → 展开为该集的节点面。节点即导航项。
- **项目总览**:多集汇总。每行一集:进度条(按节点分段,非百分比)+ 当前节点 + 真实产物计数。agent 卡住等回答的剧集在此显著提示。
- **剧集视图**:该集流程条 + 当前节点面板。surface 节点直接进对应编辑器;交付物节点展开为上传/版本/审阅区。交付物型节点在流程条上以**虚线边框**区分。
- **阶段卡瘦身**:负责人/成员/排期收进折叠区,默认只显示"当前在做什么 + 下一步"。完成条件明写在卡上(如"11 场全部出卡 — 现在 0/11,做完自动完成")。
- **设置**:模板与阶段配置移入设置页(复用已有 WorkflowTemplateEditor)。

⚠️ 新增的进度条 / 虚线边框 / 节点面板一律用语义色 token(ok/warn/danger/info/agent),**不得引入 indigo/amber 等旧色相字面类名**——K1 配色重映射后这些名字已失去原语义,仓库已因此返工过。

## 7. 迁移与兼容

生产实况:`project_stage_nodes` 仅有「个人项目测试 1」在 #1677 后新挂的一套(11 节点),其余项目为 0。`workflow_id` 是 mig 047 的遗留列(全表为空,与 M1 无关);`current_node_id` 则是 M1 的活游标,该项目已指向其 Script 节点。

**"迁移成本近乎为零"只对数据成立,对代码不成立**(评审指正):库里只有 11 行节点要清,但游标下沉要改的是 `advance_service.py`(~630 行,前进/后退/依赖/审阅/交付物门禁全按项目单游标建模)、`project_stage_nodes_repository.set_current_node_id`、`instantiation.py`,以及至少 6 个前端组件(WorkspaceStageBoard / WorkflowStrip / WorkflowSection / WorkspaceSidebar / WorkspaceTopBar / nodeStatus / issueFlow)与 4 套 e2e。**数据迁移几乎免费,代码改造是本设计的主要工作量。**

数据侧处理:

- 已挂的那套项目级节点:删除后按剧集重挂,不写通用迁移脚本
- `episode_id IS NULL` 的节点视为遗留,UI 不展示;列保持可空只为不阻断历史行
- 模板里的 `Canvas (AI Generation)` 节点:新实例化不再产生;已存在的实例节点随上一条一并清理
- 旧 SOP `project_stages`(15 行)不动,与本设计无关

## 8. 不做 / 边界

- 不动交付物的版本/审阅链路本身(用户明示"后面再丰富")
- 不做跨集依赖(如 Ep2 分镜依赖 Ep1 定稿)——先让单集链跑通
- 不动 agent 派发/needs_input 机制,只是宿主从项目节点变为剧集节点
- 节拍/场景不单列为节点,它们是 script 面内部的结构
- agent 的工具、权限、数据隔离、场景编号:见配套 spec,**本设计不依赖它先完成**
