# 编剧域 Agent 层 — 工具 / 权限 / 隔离 / 编号 设计

日期:2026-08-04 ｜ 状态:待用户确认 ｜ 配套:[`2026-08-04-episode-level-workflow-design.md`](2026-08-04-episode-level-workflow-design.md)

**独立性(修正)**:两篇大体可分头实施,但有一处真实依赖——§3.2 的"派发时钉死 scope"若要做到**剧集粒度**,依赖 spec1 给 `project_stage_nodes` 加上 `episode_id`;在那之前只能绑到**项目**粒度(+ 手动指定 script_id)。本篇威胁模型举的核心场景(跨集注入错配)恰恰发生在"agent 挂在工作流节点上执行"时,故剧集粒度的完整防护需 spec1 先行。项目粒度的隔离、编号、工具、编辑契约**不受此限**,可先做。

## 0. 为什么单独成篇

结构层(工作流下沉)改的是"东西摆在哪";本篇改的是"**agent 能碰什么、怎么碰、碰错了谁挡住**"。后者带安全后果,值得单独把关,且实施节奏不同——结构层可以先上线。

## 1. 现状核查(均已在生产库/代码中核实)

| 事项 | 实情 |
|---|---|
| 图像生成后端 | **完整可用**。`script_shot_generate` DBOS 工作流:镜头标签+描述+场景标题 → 拼提示词 → provider → 落 Tier-1 存储 → 回写同源 `image_url`(专门防 provider 临时 CDN 链接过期) |
| agent 能否调用生成 | **不能**。`GenerateImage`/`GenerateVideo` 被 `FEATURE_AGENT_MEDIA_TOOLS` 环境变量挡着,默认关 |
| agent 手上的工具 | `finish_issue` / `resource_fetch` / `skill` / `delegate`(端到端已坏) / `generate_media`(默认关)。**没有任何编剧域工具**——读不到场景、写不了镜头卡 |
| `resource_fetch` 在 issue 里可用吗 | 否。它要求 turn 携带附件,而 `issue_agent_executor` 调 `run_session_turn` **不传 attachments** |
| per-agent 权限框架 | **存在,但姿态相反的两半,不能笼统当作"现成框架"**:<br>· `agent_chat_caps.py`(只管团队聊天参与权)确实 **fail-closed**,`_as_bool` 只认字面 `True`<br>· `capability_gate.py`(真正的**工具执行闸门**)是 **fail-OPEN + 黑名单**:docstring 明写"never raises — a malformed profile fails open",`:53` 用 `except Exception` 把任何异常变成放行;`tool_blacklist` 未列入即允许;且只有"整个工具 block/allow"二元,没有 read/propose/write 分级<br>· `capability_profile` 顶层已承载 `tool_blacklist`/`allowed_skills`/`max_parallel_delegates`/`context_budget_tokens`,与 `chat.*` 平行(生产里目前仅 `storyboard` 一个 agent 填了 `chat.*`) |
| 场景内容结构 | `script_scenes.content_json` 是**元素数组,每元素带稳定 id**(如 `"id": "el_8cde5e3a"`) |
| `content_version` | **是操作序列水位**,不是手动里程碑。`content_version == MAX(op_seq)`,每次 `apply_element_ops` 递增(`version_service.py:23-25`);`script_scene_repository.py:130` 已有 `VersionConflict` 异常,编辑器提交时本就携带"上次读到的版本"(`schemas/script.py:183`)。**乐观并发通道已存在,不需另造**。<br>⚠️ 用户口述"content_version 是我手动保存的阶段性版本"——经核对那指的是右栏**版本历史**,走 `script_commits`(命名里程碑),与本列同名不同物 |
| 场景编号 | `script_scenes` 无编号列,只有 `sort_order`;显示号由前端按顺序算,插入即漂。稳定机器句柄是 `id`(雪花) |
| RLS | `script_scenes` / `script_shots` / `episodes` 各只有 **1 条策略**(service_role 全权),即"除后端外谁都读不到";而 `projects`/`resources`/`canvases`/`script_projects` 各 4 条(有真正的租户策略) |

## 2. 权限:媒体能力按 agent 授权,但**必须新建 fail-closed 闸门**

全站 env 开关是**全有或全无**——想给分镜 agent 生成图的能力,等于给了所有 agent 生成视频的能力。所以按 agent 授权的方向是对的。

**但"挂进现成框架即可"是错的**(自审+评审共同发现):真正执行工具闸门的 `capability_gate.py` 是 **fail-open + 黑名单 + 二元 block/allow**。若把媒体生成/删除/写入分级挂上去,继承到的是"配置写错就放行"——这恰好打穿 §3 威胁模型要防的东西。

**因此本设计要求新建一条 fail-closed 的授权判定**,与既有 gate 并存而非混用:

- **默认拒绝**:能力未显式授予即无权;解析异常按拒绝处理(与 `agent_chat_caps` 同姿态,与 `capability_gate` 相反)
- **白名单**语义,不是黑名单
- 只覆盖**高危能力**(写入/删除/媒体生成/发布/跨域读取);既有的 `tool_blacklist` 等低危调优保持现状,不强行统一
- 判定点在**工具执行器**内,不在提示词里(§3.1-3)

⚠️ 实施注意:`capability_gate` 的 fail-open 是**刻意设计**("配置手滑不该让 agent 变砖")。新闸门要在"高危默认拒"和"别把 agent 弄瘫"之间划清边界——**判据是能力的破坏力,不是统一姿态**。

**应当补齐的权限维度**(按危险程度):

| 权限 | 取值 | 说明 |
|---|---|---|
| **写入分级** | `read` / `propose` / `write` | 最重要一档。`propose` = 产出待人接受的修改,不落库。**模块默认 `none`(什么都不给),`propose` 由 seed agent 显式授予**——A1 实施时的修正:让"默认"更严,授权走 agent 配置,而不是让解析器自带一个宽松底线 |
| **删除** | 布尔,默认否 | 单独一档;不授时 agent 只能标记不能删。误删一场戏的代价不对称 |
| **媒体生成** | `image` / `video` 分别授权 | 有真实成本 → 除开关外还需单次上限;日额度复用已有的项目级配额 |
| **数据域** | 见 §3 | 由**派发时服务端绑定**,不是 agent 自选 |
| **跨集读取** | 布尔,默认否 | 分镜 agent 为连贯性读别集,需显式授权 |
| **对外发布/分发** | 布尔,默认否 | 绝不默认给 |

## 3. 隔离:三层防御

### 3.1 威胁模型(为什么现有做法在装工具后不够)

先纠正一个易误读点:那三张表 RLS 开着且只有 service_role 策略,意味着**除后端外谁都读不到**——不是敞口。真正的问题是:**所有访问都经后端,而后端即将被"模型生成的 id"驱动**。

1. **模型给的 id 不是授权凭据**。现有端点绑定 URL + 调用者身份;工具参数由模型产生,可能是它在别处见过的、或编造的 id。
2. **confused deputy**:工具以 service_role 权限、代表某个用户执行,授权判断必须对着**发起会话的人**做。
3. **提示注入是活路径**:剧本正文进入模型上下文;强制点必须在**执行器**里,不能只写在提示词里。
4. **join 问题**:`script_scenes` 无租户列,授权需 `script_id → script_projects → project_id/team_id` 一路 join。每个工具各写一遍 → 漏一次即跨租户读取。

### 3.2 三层(按性价比排序)

**① 派发时钉死作用域(最有效)**
一次 agent run 携带**服务端绑定、不可变**的 scope(项目 + 剧集 [+ 场景])。工具只在 scope 内解析 id——模型不是"请求被拒绝",而是**根本没有句柄指向范围外**。

实证支持:laper.ai 的 agent 收到注入后,第一步是**不信任注入、先调工具核实"这场是否真属于这一集"**(因为 episode_id 变了)。这个防御性行为很好,但它之所以必要,正是因为作用域来自可疑输入。服务端绑定后,该错配在结构上不可能发生。

**② 唯一解析器**
`resolve_scene(scene_id, scope) -> Scene | Denied` 一个收口函数,那个 join 只写一遍、只测一遍。禁止各工具自行实现可见性判断。

**③ RLS 兜底(可后置)**
给三张表加真正的租户策略,并让工具读写走**带调用者身份的非 service_role 连接**。应用层漏一处时数据库仍能挡。代价:策略需含 join,不便宜——故列第三,但不可遗忘。

**外加**:每次工具调用记审计(agent / 实际用户 / scope / 触及的 id)。

## 4. 场景编号

### 4.1 问题的真实形态

用户以 laper 实例质疑本条,核对后修正表述:laper **两个都传了**——`scene_id`(稳定不透明句柄)与 `current_scene: 01`(人看的号),正是"机器用 id、人看用号"的双轨模式,这部分它做对了。

问题不在有无编号,而在**那个号数的是什么**。证据是 laper 的 agent 自己说的:

> 「这一镜的场景编号我用了 01-xx(第 1 场);但你现在的正文在第 2 集,而**同一集的另一场已经用过 01-01 这类号**。如果希望每场**按自己场号走**,告诉我**这场实际是第几场**,我批量改镜号。」

它在向人索要"这场实际的场号"——说明 `current_scene: 01` 并非该场在本集中的固定场次(推测为视图/板相关的位置索引;无法读源码验证,依据是 agent 自述)。两场同得 01 → **镜号 `01-01` 撞车**。

**镜号从场号派生,所以场号不稳 = 下游引用全废**——镜号正是分镜表/VFX/剪辑/对外沟通引用的东西。

### 4.2 方案:写作期派生、锁定期冻结、插入用字母

沿用剧本行业既有做法(不是新发明):

- **写作期**:场号随顺序派生(即今日行为),不落库
- **锁定拍摄稿**:此刻冻结,写入实值,此后永不变
- **锁定后插入**:用字母后缀 `3A` / `3B`,既有编号不重排
- **锁定后删除**:保留号并标 `OMITTED`

落地:`script_scenes.scene_number TEXT NULL` + 剧本级 `numbering_locked_at`。锁定前为空(按顺序算),锁定后为权威值。

**为什么不加自增整数列**:第 2 场后插一场,要么后面全部重排(agent 上一轮记的"场景 5"下一轮变成别的戏),要么留空洞。字母后缀是这个行业解决同一问题解决了一百年的方案。

### 4.3 注入契约

- 机器引用用 `scene_id`(我们已有 `script_scenes.id`,雪花,稳定)
- 人看的号必须**剧集内唯一且不随视图变化**
- **字段名必须诚实**:用 `scene_no_in_episode`,不用含糊的 `current_scene`——长得像场号、实际是列序号的字段是 bug 之源

## 4.5 通用准则:模型自述的东西不能当安全前置(A5 实施期得出)

A5 实测暴露的一类错误,后续阶段(A6 生成接线、A7 可见性)都会遇到,故提到 spec 层:

**同一套校验机制,面对"代码"和面对"模型"的安全强度完全不同。**

乐观锁的经典形态是"写回时带上你读到的版本号,对不上就拒"。这在编辑器上牢不可破——**代码必然回传它真实读到的值,它没有撒谎的能力**。换成 LLM 就塌了:模型可以产出任意整数。A5 还犯了加重错误——`ProposeEdit` **主动把当前版本号回显给模型**,于是模型把它填进 `ApplyEdit`,`base == current`,整段前置被跳过,作者刚打的字被无声覆盖(评审执行代码复现)。

讽刺的是当时代码已识破一半:它拒绝 `base > current`,理由写着"那等于相信模型编的数字胜过表里的事实"——**同一句话对 `base == current` 同样成立,那一档却没设防**。

**准则**:凡是把模型自述的内容当作安全前置条件,必须问一句——**服务端有没有独立的记录可以对照?** 没有的话,那个前置条件只是装饰。

**修法范式**(A5 已落地):服务端记录本次 run 实际观测到了什么(`scene_observations.py`,按 `(run_id, scene_id)` 隔离),以服务端记录为准,模型自述降级为交叉校验。附带白送"没读过就不能写"。记录缺失时**失败即拒**,绝不回退去信模型。

## 5. 工具层

### 5.1 工具集(最小可用)

| 工具 | 作用 | 权限门 |
|---|---|---|
| `ListScenes` | 列出 scope 内剧集的场次(号/标题/内外景/地点/日夜/是否有内容) | read |
| `ReadScene` | 读某场内容(返回元素数组:element_id + 类型 + 文本) | read |
| `CreateShot` / `UpdateShot` | 写镜头卡(景别/角度/运动/焦段/描述/角色标记) | write |
| `ProposeEdit` | 对选中元素提出修改建议 | propose |
| `GenerateShotImage` | 触发已有的 `script_shot_generate` 工作流 | 媒体生成 |

全部经 §3.2 的唯一解析器,全部在 scope 内。

### 5.2 编辑安全契约:复用既有 ops 通道,不另造机制

**修正(自审发现)**:早前基于"`content_version` 是手动里程碑"的判断而设计的"元素哈希前置"是多余的——该列本就是操作序列水位,且 `VersionConflict` 与"编辑器带上次读到的版本提交"的乐观并发链路**已经在跑**。agent 的写入应当走**同一条 ops 通道**,而不是新开一条旁路。

- **选区锚点** = `{scene_id, element_ids: [...]}`(元素 id 已稳定存在于 `content_json`)
- **写回前置** = 复用现有语义:携带读取时的 `content_version`,冲突由既有 `VersionConflict` 抛出
- **冲突处理**:必须**明示**("这段在你改动后变了,要基于新内容重来吗"),**绝不静默覆盖**
- **待评估的粒度问题**:现有语义是**整场**级水位——用户在同一场的别处打一个字,agent 的写回就会冲突。这对人机并发是否过严,需在实施期实测。若确证过严,再考虑元素级前置(而非现在就假定需要)。**本 spec 不预先决定**,列为实施期的第一个待验证项

### 5.3 选区必须是结构化附件,不是复制文本

| | 目标形态 | 现状 |
|---|---|---|
| 载荷 | `{scene_id, element_ids, 摘要文本}` | 原文被复制成纯文本塞进输入框 |
| 面板呈现 | 可关闭的引用胶囊(`选自 场景 1 · 2 个元素`) | 一段脱离上下文的字 |
| agent 能做什么 | 精确替换那几个元素,渲染为可接受/拒绝的修订 | 只能吐新文字,人工粘回 |

产品里已有"选自 S2"的意识,缺的是**载荷从文本换成句柄**。

### 5.4 调用可见性

`agent_run_transcript_events` 表已存在,但协作时间线**不渲染工具调用**(消息类型仅 comment / agent_run / system_status)。需把 transcript 事件接到面板与时间线,呈现为"读取剧本场景 ✓"式胶囊。生成结果以**镜头卡摘要**(镜号/一句话/焦段)呈现并可点跳到画布对应节点,并提供"本轮写入 N 张卡 + 撤销"。

## 6. 不做 / 边界

- 不重写 `script_shot_generate`(已完整,只是接上工具入口)
- 不修 `delegate`(已知端到端损坏,与本设计无关)
- 不做实时协同编辑(OT/CRDT);元素级哈希前置足以覆盖"人机并发改同一篇"的场景
- RLS 第三层可后置,但必须进路线图而非消失
- 不动交付物审阅链路

## 7. 分期

**地基期(必须先做,否则工具越多漏洞面越大)**
1. `capability_profile` 收编媒体权限 + 写入分级/删除/跨集读取维度
2. 派发时服务端绑定 scope + 唯一解析器 + 审计
3. 场景编号(派生/冻结/字母插入)+ 诚实的注入字段名

**工具期**
4. `ListScenes` / `ReadScene` / `CreateShot` / `UpdateShot`
5. 元素级编辑契约 + 选区结构化附件 + `ProposeEdit`
6. `GenerateShotImage` 接已有工作流

**呈现期**
7. transcript 事件接入面板与时间线;镜头卡摘要 + 撤销

**后置**
8. RLS 租户策略 + 非 service_role 连接

## 8. 测试口径

- 隔离:构造跨租户 id 直接喂给工具,断言拒绝且审计留痕;scope 外的同用户资源同样拒绝
- 编号:锁定后插入场次,断言既有场号不变、新场得字母后缀;镜号派生不撞
- 编辑契约:agent 读取后、写回前由第三方改动同一元素 → 断言明示失败;改动其他元素 → 断言正常写入
- 权限:未授权 agent 调 `GenerateShotImage` / `UpdateShot` → 拒绝;授权后放行
- 可见性:一次工具调用在面板与时间线各渲染一次,不重复不丢失
