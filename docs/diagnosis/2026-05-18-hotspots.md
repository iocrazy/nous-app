**Window**: 2026-05-12 → 2026-05-14, **zero since 2026-05-14**

**Sample error**:
```
ffmpeg [h264_nvenc] failed for tier 1080p:  0x55b43f24b100] Could not dynamically load CUDA
Device creation failed: -1.
[vist#0:0/h264 @ ...] Hardware device setup failed for decoder: Operation not permitted
```

**Root cause**: NAS container lost CUDA toolkit access (likely container restart wiped the GPU mount, or driver version drift). ffmpeg probed `-encoders` and saw `h264_nvenc` listed (compile-time) but couldn't actually use it at runtime → every transcode tier failed.

**Why it stopped**: PR #277 (`fix(transcode): probe encoders at runtime, not via ffmpeg -encoders`) + PR #278 (`fix(transcode): restore admin transcode_min_size_mb gate`) shipped 2026-05-14. Runtime probe now detects the nvenc-broken-but-listed state and falls back to libx264.

**Correction added 2026-05-18 post-review.** The first pass of this report flagged #2 as P0 ACTIVE based on 7-day error counts (41 errors). Cross-referencing against deploy timeline + database state shows: **PR #273 (merged 2026-05-13 22:16 +0800) already fixed this.**

### Original analysis (preserved for reference — was the pre-PR-#273 picture)

**Module**: `app.services.media.downloader.downloader`
**Count**: 41 errors aggregated into 13 distinct messages (some are the same BV retried)
**Affected videos** (distinct BVs): BV1Y4oKBEEru, BV13s536dEJj, BV1QbduBSEc8, BV12sdZB2E7L, BV1YUozBGEGp, BV1WV576tEnT — at least 6 unique videos in 5 days
**Window**: 2026-05-12 → 2026-05-15 (active)

**Failure chain** (verified at `backend/app/services/media/downloader/downloader.py:140-175, 320-410`):
1. yt-dlp completes HTTP download → MP4 lands on disk
2. `verify_video_integrity` runs `ffprobe`, finds `moov atom not found` in stderr (downloader.py:159)
3. Downloader logs `视频文件损坏: moov atom not found in video.mp4` and deletes file
4. Outer raises `Video file corrupted or incomplete: video.mp4` (line 352/409)
5. `downloader.py` strategy loop logs final: `All 1 download URLs for video bilibili_<BV>_p1 failed: URL1: download_file returned False`
6. **No retry** — task_tracking row marked failed, user sees download error

**Why moov atom missing**: bilibili's `dash` stream for some videos returns MP4 with the moov box at the END, and yt-dlp's progress streaming sometimes saves a truncated tail (likely a connection reset during fragment merging). Once truncated past the moov, ffprobe can't index the file.

**Fix options** (ordered by ROI):
1. **Add `--retries 3` + `--fragment-retries 5`** to yt-dlp invocation if not already there. Cheap, may help with the connection-reset class.
2. **Single retry with `-S "+size"` re-ordered format selection** — if first attempt fails moov check, retry with a different format pick.
3. **Switch bilibili strategy to merged-MP4-via-ffmpeg** instead of streaming-download — pulls fragments separately then `ffmpeg -c copy` re-muxes, guaranteed valid moov.

**Suggested PR scope**: option 1 + option 2 as `fix(download): retry on corrupted moov`. ~30 lines.

**Pre-existing related concern**: download.py:337 has `"Video too small (< 200KB) → CDN error response"` check (1 hit in last 7d). That's a different failure mode (CDN returning HTML/JSON instead of MP4) and is already detected. Not the same as moov atom.

**Failure point**: `drissionpage_parser.py:437` — `max_timeout_retries = 5` hit, parser gives up.

**Root cause**: Douyin tightened anti-bot. DrissionPage holds a real Chrome instance and waits for `/aweme/v1/web/aweme/detail/` XHR response; lately that XHR is either slow (>timeout) or returns empty body (anti-bot challenge intercepts).

**Fallback path** (verified): douyin parser stack is `IesDouyinParser → DrissionPageParser → ...`. When IES (yt-dlp-based) is available and DrissionPage fails, IES should handle. Need to confirm IES is actually being tried for these failures — if yes, this is just verbose logging of a successful fallback. If no, we lose 18 parses.

**Recommended diagnostic before any code change**: query whether the 18 DrissionPage failures had a successful sibling parse in the same workflow (check `task_tracking.phase = completed` for the same `parsed_media_id`). If yes — these are noise (downgrade to WARNING). If no — IES fallback isn't wiring, real bug.

**If real bug** (fallback not firing): related to investigation task #21 (`IesDouyinParser called with bilibili platform_id`) — there's already evidence parser dispatch is misrouted. Tie these two together for one investigation.

## Procedure used

```sql
-- Top hotspots (any module)
SELECT module, level, COUNT(*) AS cnt, MAX(logged_at) AS last_seen
FROM application_logs
WHERE level IN ('ERROR','CRITICAL') AND logged_at >= NOW() - INTERVAL '7 days'
GROUP BY module, level ORDER BY cnt DESC LIMIT 30;

-- Drill into a specific module
SELECT message, COUNT(*) AS cnt FROM application_logs
WHERE module = '<module>' AND level='ERROR' AND logged_at >= NOW() - INTERVAL '7 days'
GROUP BY message ORDER BY cnt DESC LIMIT 20;

-- Daily distribution (resolution verification)
SELECT DATE_TRUNC('day', logged_at) AS day, COUNT(*) FROM application_logs
WHERE module = '<module>' AND level='ERROR' AND logged_at >= NOW() - INTERVAL '14 days'
GROUP BY day ORDER BY day DESC;

-- Incident hour-by-hour breakdown
SELECT DATE_TRUNC('hour', logged_at) AS hour, module, COUNT(*) FROM application_logs
WHERE level='ERROR' AND logged_at >= '<start>' AND logged_at < '<end>'
GROUP BY hour, module ORDER BY hour, COUNT(*) DESC;
```

All queries run via Supabase MCP `execute_sql` (read-only, against production).

### Cross-reference step (added 2026-05-18 after §2 correction)

Before classifying a count-based hotspot as ACTIVE, run:

```bash
# What touched this module recently?
git log master --oneline --since="<window_start>" -- <module_path>

# Did the daily trend stop after that PR?
SELECT DATE_TRUNC('day', logged_at), COUNT(*) FROM application_logs
WHERE module = '<module>' AND level='ERROR' AND logged_at >= NOW() - INTERVAL '14 days'
GROUP BY 1 ORDER BY 1 DESC;
```

If the daily series goes to 0 right after a PR landed, the hotspot is RESOLVED, not ACTIVE. The 7-day window count is misleading when a recent fix shipped — the legacy errors still in the funnel inflate the apparent severity. Re-verify against DB state too (e.g. for #2: do any rows created AFTER the fix still show the bad shape?).
